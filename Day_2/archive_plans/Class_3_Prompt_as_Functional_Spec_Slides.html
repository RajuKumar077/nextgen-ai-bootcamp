Class 2.1  ·  Phase 2 · FS templateProject NOVA-AP · Sprint 1

Why each section matters

Role → vocabulary and depth

An "SAP procurement analyst" writes differently from a "customer service agent".

Task → one clear verb

Summarise · classify · extract · draft · compare. Not "look at this".

Context → your business rules

The model has never seen your policies. Only you can specify them.

Format + Rules → testable output

A fixed layout and explicit validations make the output checkable.

Context is where SAP expertise is irreplaceable.
Class 2.1  ·  Phase 2 · FS templateProject NOVA-AP · Sprint 1

System prompt vs user prompt

System prompt · set once by the solution

Configuration

Role, business rules, output layout, validations. Hidden from end users, identical for every email.

User prompt · changes every call

Transaction data

The specific email or document to process, inside <<< >>>.

SAP LENS · customising (system prompt) vs the business document being posted (user prompt)
The notebook helpers support both: ask_ai(question, system=...). We use the system prompt seriously in Sprint 2 security.

Business rules must be written like configuration

Vague rule

must go to the finance controller.
Model output

Run B: Escalate? Yes: “price dispute” (right answer, wrong reason)
Explicit rule
₹5 lakh = ₹5,00,000.
If amount is ABOVE ₹5,00,000 → Finance Controller.
Otherwise → AP team.
Model output
Escalate to Finance Controller? Yes (Amount > ₹5,00,000), on every run
₹7,80,000 is above ₹5 lakh. With the vague rule, the small model compared the numbers inconsistently.

Class 2.1  ·  Phase 3 · Impact analysisProject NOVA-AP · Sprint 1

Interpretation

Format drives completeness

Without a layout, required fields drop out (3/5)

Rules control scope

Without them: 71 words instead of ~45, with content nobody asked for

Context drives correctness

All fields can be present and the decision still wrong (Phase 2)

A test that only checks presence misses wrong decisions. Test the reasoning too.
An important nuance about acceptance testing.

Three patterns, three purposes

Zero-shot

The requirement only, with no examples

Use for: simple, common tasks

Few-shot

The requirement plus 2–3 reference examples

Use for: fixed categories and a consistent style

Stakeholder view

The same input written for a specific audience

Use for: tone, depth, length

Class 2.1  ·  Phase 4 · Design patternsProject NOVA-AP · Sprint 1

Writing good reference examples

Representative

Real-looking emails from your own mailbox, anonymised

Varied

One per category; different wording and length

Exact format

Show the output exactly as you want it, label only

Few, not many

2–5 is usually enough; more costs tokens and time

Watch out for bias: if most examples are DELIVERY_DELAY, the model leans towards DELIVERY_DELAY.
Practical guidance for building few-shot sets on real projects.

Risk flag raised during testing

Email DClassified: OTHER
"Please update our bank details for future payments; new letter attached."
A bank-detail change request is one of the most common payment-fraud patterns in accounts payable.

Classification is correct. Acting on it automatically would be a control failure.

Policy: written confirmation + call-back. Day 4 covers guardrails.

Common specification defects

No layout

Fields go missing; the structure varies

Vague rules

"5 lakh" vs ₹5,00,000

No examples

The model invents its own categories

No validations

Guessing and over-long output

Data not separated

No <<< >>> markers, which is a security risk

Each defect was shown live today.
