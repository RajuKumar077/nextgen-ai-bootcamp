Role and Task

PFCG

Role: who is calling

An "SAP procurement analyst" gets a different answer from a "customer service agent". Different vocabulary, depth and focus, the way a role changes what a user sees.

SE37 · short text

Task: one function, one job

A good function module does one thing. So should a prompt: summarise, classify, extract or draft, not "look at this and help".

Z_LLM_ASK›Class 2.1 · Step 2 · InterfaceSE37

Context: the model has no customizing

" Normal code reads customizing at runtime
SELECT SINGLE * FROM zap_escal_rule
  INTO @ls_rule
  WHERE bukrs = @lv_bukrs.

" Z_LLM_ASK has no tables to read.
" The rule must travel in the call:
"Above ₹5,00,000 → Finance Controller"

The model has never seen your SPRO, your thresholds or your approvers.

If a rule matters, pass it as a parameter, every call.

This is where functional expertise is irreplaceable.
Z_LLM_ASK›Class 2.1 · Step 2 · InterfaceSE37

Format and Rules: structure and checks

SE11

Format: a fixed structure

Vendor · Invoice number · PO number · Amount · Issue · Escalate (Yes/No + reason) · Next action. The same fields on every call, so they can be parsed and compared.

MESSAGE E

Rules: the checks

"If a value is not in the email, write Not stated. Do not guess. Max 20 words per line." That's the AI version of an input check that stops bad data.

Z_LLM_ASK›Class 2.1 · Step 2 · InterfaceSE37

System prompt vs user prompt

System prompt · set once by the developer

Like customizing

Role, rules, structure, checks. Identical for every call; end users never see it.

User prompt · changes every call

Like the business document

The actual email or text to process, wrapped in <<< >>> markers.

The notebook helpers support both: ask_ai(question, system=…). The split matters for security in Class 2.2.
Z_LLM_ASK›Class 2.1 · Step 2 · InterfaceNotebookCell 2

The full call

ROLE     You are an SAP procurement analyst.
TASK     Summarise this invoice dispute email.
CONTEXT  ₹5 lakh = ₹5,00,000. ABOVE ₹5,00,000 → escalate to the Finance Controller. Otherwise → AP team.
FORMAT   Vendor · Invoice number · PO number · Invoice amount · Issue · Escalate? (Yes/No + reason) · Next action
RULES    If a value is not in the email, write "Not stated". Do not guess. Max 20 words per line.
PAYLOAD  <<< …vendor email… >>>

The <<< >>> markers separate our parameters from external data, like escaping input before dynamic SQL.

Customizing → correctness

A test that only checks presence misses wrong decisions. Test the logic too, which is what ABAP Unit is for.

Good example entries: like good test data

Realistic

Anonymised emails from your own mailbox

One per value

Cover every category at least once

Exact output

Show the result exactly as you want it back

Few

2–5 is usually enough; more costs tokens

Watch for bias: if most examples are DELIVERY_DELAY, the model leans towards DELIVERY_DELAY.
